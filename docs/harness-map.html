01

一句話原則：規則與執行分離

Harness 本身只是本機的 control plane（控制面）。它決定「怎麼跑、誰跑、要不要驗」，但不綁死任何一台機器、帳號或平台。

05

主 session 怎麼呼叫 Codex 與 agy

從收到任務到派工、驗證的完整流程。關鍵：授權是「核准整張 Route Plan」一次給足，不用每個節點再追問。

  1. 主 session 收任務 → 分類 → 建 Route Plan
    為每個執行節點寫死 owner + model：思考類留給自己，粗工標給 Codex，大脈絡分析/獨立審查標給 agy。
  2. 使用者 核准 Route Plan＝觸發授權
    這一步滿足「不主動 spawn subagent」政策——使用者透過核准明確要求了。核准後 Codex/agy 節點不需逐一再問。
  3. Codex 接粗工節點
    主 session 以 codex:codex-rescue 呼叫，不傳 model / effort（舊版 helper 白名單無 max，靠 CLI 預設最穩）。長任務背景跑，取回結果由主 session 整合。
  4. agy 接分析 / 獨立審查節點
    大 context 通讀或當第三家族的獨立審查者。這台只能 advisory，結論回主 session 由使用者裁決。
  5. 主 session 整合 → 驗證 → 回報
    驗證時 executor 與 verifier 必須是不同身分/模型。任何節點跑歪、範圍變動即標 有問題 停下。
🔐安全敏感節點
authn/authz、憑證/secrets、加密、輸入驗證、漏洞分析 永不進 Codex。執行後的審查交由主 session 指定、且與執行者不同的模型，杜絕自做自審。
✋停下問使用者
Codex/agy 節點若碰到範圍變動或不可逆/外部變更（push、發布、刪除、外部 mutation），一律停下問使用者，不自動衝。
🧭fallback 不擴權
指定平台不可用時預設由主 Agent 接手並記錄 requested / actual 差異；不得因 fallback 自動擴大 allowed paths 或任務範圍。
06

驗證要派多重？

驗證不是每個節點固定派一個，而是依 profile 節流；使用者明確指定的 mode 優先。

Profile預設驗證獨立性節點 verifier 上限說明
Simplenonedisabled0只做輕量 plan contract 檢查，不派獨立 verifier。
Standardfinalpreferred0任務最後統一驗證一次；不同平台 verifier 優先，不可用可降級但須留 gap。
Complexnode-or-finalrequired1高風險/跨平台節點才派 node verifier；required 需可辨識的不同實際身分才過閘。
The Invariant · 不變式
「誰做的，不由自己審。」
審查者由主 session 指派，刻意選與執行者不同的模型——這是整套多執行者設計存在的理由。
